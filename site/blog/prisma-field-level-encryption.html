Field-level encryption in Postgres with a Prisma client extension

17 September 2026·7 min

Adding minidauth to Cal.com's scheduling platform came down to one Prisma client extension, switched off unless an environment variable is set. The encryption call itself was the easy part. The decisions that took thought were which fields to seal, what should happen when the encryption service is down, and how to stop a value that only looks encrypted from being trusted. They apply to any Postgres app on Prisma, whatever does the encrypting.

Why an extension rather than the call sites

A Prisma client extension wraps every query on the shared client, so create, update, upsert, createMany and the find family all pass through one place. Cal.com writes bookings from a lot of routes, and patching each of them would more or less guarantee that some path eventually writes plaintext. With the extension, a route added next year gets sealing without anyone having to remember it. The Formbricks fork uses the same shape for survey answers.

Decide what not to seal

A sealed column holds ciphertext, so Postgres can no longer sort, filter or search on it. That makes the field list a design decision rather than "everything personal". The Cal.com fork seals these: 

const SEALED: Record<string, string[]> = {
  attendee: ["name", "phoneNumber"],
  booking: ["title", "description"],
};

Two personal fields are left in the clear on purpose. An attendee's email is an indexed lookup key, used for de-duplication and seats, so sealing it would break those queries. A booking's location is branched on by value, since it can be an integration name, a URL or a street address, so sealing it would break routing rather than just hide it. The rule that fell out of this: seal the personal fields your database never needs to look inside.

Nested writes and included reads

A booking is usually created together with its attendees and read back with them included. An extension that only looked at the top-level model would send the attendees' names to Postgres in plaintext. The fork keeps a small map of relations to follow, so a nested create and an include both reach the child's sealed fields: 

const RELATIONS: Record<string, Record<string, string>> = {
  booking: { attendees: "attendee" },
  attendee: { booking: "booking" },
};

On the write side it follows create, createMany.data and connectOrCreate.create, which covers every way Cal.com creates attendees.

Writes fail closed, reads fail sealed

The two directions fail in opposite ways, deliberately. If the sealing service can't be reached during a write, the write throws. Storing plaintext because a dependency was down would quietly undo the whole point of the change, and nobody would notice until much later.

On a read, the safer choice is the reverse. If there's no reader identity on the request, the reader doesn't hold the role, or the service is down, the field comes back still sealed and the page renders anyway. Ciphertext on a screen is a visible and harmless failure, where a booking page that crashes is neither.

Don't trust a value that looks encrypted

Sealed values are stored as ms1: followed by the ciphertext. The obvious optimisation is to skip anything that already starts with that prefix so it doesn't get sealed twice. The fork doesn't do that, because a client can type the prefix as easily as anything else. If the extension trusted it, someone could submit plaintext beginning with ms1: and have it land as-is in a column everyone believes is sealed.

Only the network can tell a real seal from a forged one, since real ones carry a signature from the vendor key. So every non-empty string headed for a sealed column is sent for sealing, and the service decides what comes back. In normal use this doesn't double-seal anything, because the app only ever handles opened values.

One round trip, not one per field

A page of bookings with their attendees can hold dozens of sealed values. The extension collects every sealed field in a result, including the included relations, and opens them in one batch: a single fan-out to the network instead of one per field. The fork's notes point at the next step for production, which is to protect one data key per record with the network and encrypt that record's fields locally under it, so the cost is one network operation per record however many fields it has.

Who is reading

There's no service account that can open everything. The session middleware attaches the signed-in user to each authenticated request, and the sealing service decrypts as that user, and only if the quorum's grant says they hold the reading role. A request with no reader gets ciphertext. That takes away the most useful thing an attacker could hope to find on the server, which is a credential that decrypts whatever it's asked to.

What you give up

Search and sort on the sealed columns, a network call on reads that open fields, and some care about which fields are really lookup keys. In return, a copy of the database or a backup holds ciphertext for the fields that matter, and whether anyone can read them depends on a role your admins approved rather than on the app.

The Cal.diy project page summarises what the fork seals, and the fork itself has the full change. If you're doing this to your own Prisma app and get stuck, ask in the Discord.
