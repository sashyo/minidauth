Keep roles out of your auth provider's token

17 September 2026·6 min

Every major auth provider gives you a way to put your own data into the token it issues. Supabase copies app_metadata into the access token, Clerk can add metadata to its session token, an Auth0 Action can add claims, and Cognito has its Pre Token Generation trigger. They're useful features, and putting a user's roles there is one of the most common ways apps use them. When we wired minidauth into each of these, every example ended up doing the opposite on purpose, and the reason is worth spelling out.

Who can grant the role

A token is signed by the provider on behalf of your project. Anything your project can put into that token, it can also put into anyone's token. That's exactly right when your project is meant to be the authority on who holds which role, which is the case for most apps. It stops being right when the goal is that no single party, including your app and the people who run it, can grant access alone. A role in a token your project can mint is a role your project can grant itself.

So in every example the token carries identity and nothing more. Roles come from somewhere the app can read but can't write: a grant record that only changes once several admins have approved the change and the Tide network has signed it.

What goes in the token instead

Enough to say who the user is, plus a link to their Tide identity, called a vuid, kept in a field the user can't edit:

ProviderWhere the link lives
Supabaseapp_metadata.tide_vuid, written with the service role key
ClerkprivateMetadata.tideVuid
Auth0app_metadata.tide_vuid
Cognitocustom:tide_vuid
Better Autha tideVuid column with input: false

The rule for picking the field is the same everywhere: the user must not be able to change it. Supabase's user_metadata and Clerk's public metadata can be written from the client, so they're the wrong place for it. On Cognito, if a Pre Token Generation trigger copies anything into the token, it should copy the vuid and nothing else.

Reading roles on every request

The protected route in each example asks minidauth what the user holds, every time, instead of trusting a claim in the token: 

// the vuid comes from the field in the table above
const roles = await minidauth.rolesFor(user.tideVuid);
if (!roles.includes("vault-reader")) return res.status(403).end();

One side effect is useful on its own: a revoked role takes effect on the next request rather than whenever the token happens to expire. And nothing an admin changes in the provider's dashboard alters the answer, because the provider isn't where the answer lives.

Provider details that caught us out

Supabase

Because app_metadata is copied into the access token, a token issued before the user linked their Tide identity doesn't contain the vuid. The example asks the user to sign in again rather than pretending the token refreshed.

Clerk

The Tide sign-in returns to your app with a cross-site navigation, and on a Clerk development instance authenticateRequest can't identify the caller on that request. The example sets its own short-lived httpOnly, SameSite=Lax cookie when linking starts and reads it on the way back, which is worth doing in production as well.

Auth0

Writing app_metadata needs the application authorised for the Management API with update:users. In the API Access tab that's under Client Access (machine to machine), not User-delegated Access, and it's the easiest step to miss.

Cognito

The example's setup script creates the user pool with a tide_vuid attribute, the app client and the hosted UI domain, and npm run teardown removes them again, so trying it doesn't leave anything behind in your AWS account.

When it's worth the extra call

If your app is the right authority for roles, keep them in the token. It's simpler and it saves a request. This pattern earns its keep when the data behind a role is sensitive enough that access should depend on more than one party, which is the reason minidauth exists in the first place.

Each provider has a page with the full setup: Supabase, Clerk, Auth0, Cognito and Better Auth. If yours isn't there, ask in the Discord.
